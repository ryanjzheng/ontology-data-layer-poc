Ontology Data Layer POC

Object Storage V2, mapped onto Databricks

The same object-storage behaviors, two sides. Palantir Object Storage V2 as the conceptual model; Unity Catalog ⊕ Lakebase as the concrete build. Layers that sit at the same height are the same capability — the ✓ marks a faithful behavioral match.

Why the mapping is principled, not forced

V2 exposes two read surfaces — an immediate object read and an async materialized dataset. Our split reproduces that duality exactly: Lakebase overlay = the immediate read, UC GOLD / MV = the materialized dataset. Rows 4 and 5 aren’t two guesses; they’re the same two surfaces V2 already has.

≈ Approximate

Incremental indexing (billions of objects), low-latency streaming ingest, and 10k-object/action throughput map in shape but aren’t proven at that scale here.

⚠ Build gap

Per-object row-level security is native in V2. For us it’s a build task — UC row filters + Lakebase RLS — not a freebie.

Out of scope

V2 is the storage substrate only. The object-type registry, OSDK, Functions runtime, Actions validation, and Link Types sit above it.
