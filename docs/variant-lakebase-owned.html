Edits owned by Lakebase

Same nodes as the plan — the authority flips. Lakebase Postgres becomes the durable system of record for edits (not a rebuildable buffer), so app read and write and reconcile all happen in one engine. UC BASE stays the source of truth; the UC edit copy becomes a derived, disposable BI feed. Pick this when write velocity/concurrency is the constraint.

When to pick this over the plan

When write velocity/concurrency is the binding constraint and you need authoritative transactional edit semantics — many concurrent editors, optimistic-lock conflict detection that must stick, or multi-object atomic edit batches. The plan's UC-owned buffer flattens all of that to last-write-wins at MERGE time; here it's real and durable at commit. The cost you take on: Postgres becomes your durability tier (HA + backups), and BI is always a lagged derived view rather than a near-equal second surface.

Note the topology is ~identical to the plan — same five boxes. Only two things change on the canvas: the edit store fuses into the app-serving Lakebase, and the Lakebase→UC edge goes dashed. Everything else in the table follows from moving the ◆ SoR · edits badge from UC to Lakebase.
