Ontology Data Layer POC · first-principles model

Reconciling two writers into one servable truth

Not a copy of Palantir — the irreducible problem underneath it. Two writers of different authority (upstream source vs app edits) meet at one reconcile step governed by a per-property precedence policy, and fan out to a fast app read and a governed BI read. Trace any scenario along the numbered, color-coded flows.

Scenarios to play

ScenarioTraceResult
App reads an object⑥ ← (④ ⊕ ⑤ via ⑨) → ②Reconciled value, edit precedence applied per property, served fast.
User edits a property③ → ⑤ → ⑥ → ②Lands only in the Edit Store; visible on next read. BASE untouched.
Upstream re-ingests an edited row① → ④ → ⑨Policy decides: edit-wins keeps the edit (refresh-resilient); source-authoritative lets the fresh source override.
Upstream re-ingests a non-edited row① → ④ → ⑥/⑦No edit to win; new source value flows straight through.
Revert / drop an edit⑧ → ⑤ empty → ④Reconcile falls back to the (possibly newly-refreshed) source value.
BI / analytics query④ ⊕ ⑤ via ⑨ → ⑦Same precedence, materialized asynchronously — lags the app read by the refresh cadence.
Conflict: user edited field X, upstream pushes an authoritative X⑨ (per field)The case where “edits always win” is a bug. Per-property policy is what resolves it correctly.

Where the logical nodes live physically (the UC ⊕ Lakebase fork)

Pick one authoritative owner for the Edit Store based on edit write velocity; the other engine holds a derived copy. This is what makes the mapping clean instead of maintaining two durable edit copies.

Edits owned by Lakebase — high-concurrency interactive writes

Edit Store + App-serving = the same Lakebase (Postgres is durable + transactional). UC BASE = source. Reconcile = a Postgres overlay for the app + a periodic sync to UC GOLD for BI (the UC edit copy is derived/disposable).

Edits owned by UC Delta — low / batchy edits

Edit Store = UC app_changes (one engine, no reverse-sync seam). App-serving Lakebase = a read-through cache of the reconciled view. Closest to Palantir’s single edit store; simplest to operate.

The two facts that pick the branch — does upstream re-ingest edited rows? (if no, you don’t need this at all) and what’s the edit write velocity? (picks the owner).
